# REPORTS

Тут зберігаються результати агентних кампаній.

## Імена звітів

Report-файли називаються тільки за ID задачі:

```text
01.md
30-e.md
37-e.md
41-e.md
```

Час створення не записується в назву або metadata звіту.

Повторний запуск:

```text
04__retry-01.md
04__retry-02.md
```

Основний report не перезаписується автоматично.

## Структура

```text
REPORTS/
└── <target-key>/
    ├── CURRENT_EDITING.md
    ├── CURRENT_WRITING.md
    └── <run-folder>/
        ├── RUN.md
        ├── CLAIMS/
        │   └── <PIPELINE>/
        │       └── <task-id>.md
        ├── EDITING/
        │   ├── 01.md
        │   ├── 30-e.md
        │   └── 37-e.md
        └── WRITING/
            ├── 01.md
            ├── 02-e.md
            └── 41-e.md
```

Run-папка може містити timestamp для розрізнення кампаній. Звіти — ні.

## Вибір поточного run

1. `CURRENT_<PIPELINE>.md` має пріоритет, якщо веде на OPEN run.
2. Якщо pointer відсутній або зламаний — серед run-папок цього target бери найсвіжішу OPEN кампанію.
3. Не бери run іншої арки.

## Як визначити виконану задачу

- `04.md` = task `04`.
- `30-e.md` = task `30-e`.
- `30-e__retry-01.md`, `30-e__retry-02.md` = повтори task `30-e`.
- Суфікс `-e` є частиною task ID і означає наявність required reports.

## Автоматичний dispatcher

Коли task ID не задано:
1. знайти target;
2. знайти поточний OPEN run;
3. прочитати INDEX;
4. перевірити наявні report-файли;
5. перевірити CLAIMS;
6. перевірити dependencies/gates;
7. взяти перший runnable task за AUTO DISPATCH ORDER;
8. створити атомарний claim;
9. виконати;
10. записати report `<task-id>.md`;
11. видалити claim.

Наявний claim без report означає: task уже взяв інший worker.

## Готовність required report

Required report = READY тільки коли:
- файл потрібного ID існує;
- він не порожній;
- містить змістовний результат після metadata/header;
- має `Status: COMPLETE`;
- target/run збігаються з поточною кампанією.

Якщо є retry, для READY використовуй COMPLETE retry з найбільшим номером.

Інакше статус входу = `NOT_READY`.

Для dependent task:
- хоча б один required = NOT_READY → `WAITING_FOR_REPORTS`;
- не створювати фінальний report dependent task;
- не заповнювати відсутній input власними припущеннями.

Для auto-dispatch:
- якщо є інший runnable task — виконати його;
- якщо runnable tasks немає — `NO_RUNNABLE_TASKS` і список відсутніх/claimed inputs.

## Завершений pipeline / final handoff

Фінальний основний report залежить від pipeline:

- `EDITING` → `37-e.md`;
- `WRITING` → `41.md`.

Коли новий worker отримує загальну команду:
- якщо фінальний report відсутній або не COMPLETE → працює за dispatcher;
- якщо фінальний report COMPLETE → повертає готовий результат користувачу й не створює нового run.

Пріоритет готового файла:
1. файл із поля `Final artifact:` у COMPLETE фінальному report;
2. якщо такого поля/файла немає — сам фінальний report.

Новий run після COMPLETE фінального report створюється тільки за явною командою користувача на новий запуск/retry.

## Кілька повних запусків одного task

Якщо той самий task реально відпрацював більше одного разу в межах одного run, усі повні результати зберігаються.

Іменування:

```text
03.md
03__02.md
03__03.md

30-e.md
30-e__02.md
30-e__03.md
```

- `03.md` — перший COMPLETE результат task 03.
- `03__02.md` — другий COMPLETE результат task 03.
- `30-e.md` — перший COMPLETE результат task 30-e.
- `30-e__02.md` — другий COMPLETE результат task 30-e.
- Не використовуй слова `duplicate`, `alt` або timestamp у назвах.

Для auto-dispatch task вважається виконаним, якщо існує хоча б один COMPLETE файл серії.

Для звичайного required_report наявність хоча б одного COMPLETE файла серії задовольняє залежність.

## Фінальний збір усіх виконаних агентів

Фінальний оркестратор не обмежується одним файлом на task ID: для EDITING це 37-e, для WRITING — 41-e.

Перед фінальним синтезом він:
1. переглядає всю папку REPORTS поточного pipeline;
2. для кожного task ID збирає всі COMPLETE файли серії: `03.md`, `03__02.md`, `03__03.md` тощо;
3. читає всі ці результати;
4. не рахує їх як незалежне голосування більшістю;
5. використовує кілька запусків одного task як окремі спостереження однієї аналітичної функції;
6. при суперечності між ними арбітрує за першоджерелом.

Жоден COMPLETE звіт агента, який реально працював у цьому run, не повинен бути мовчки виключений із фінального оркестратора.


## Legacy `-e` transition

Якщо task був уже CLAIMED до введення суфікса `-e`, старий unsuffixed claim/report тимчасово вважається alias нового dependent ID.

Приклад:
- старий `30.md` claim = `30-e` зайнятий;
- не створюй паралельний `30-e` claim;
- якщо старий worker завершить `30.md`, перенеси його результат у `30-e.md` і видали legacy-файл/claim;
- після міграції використовуй тільки `30-e`.
