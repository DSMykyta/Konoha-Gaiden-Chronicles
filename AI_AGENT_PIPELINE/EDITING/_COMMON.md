# EDITING — спільні правила

# Система 36+ незалежних агентів для глибокого аналізу прози

## Runtime write boundary

Для pipeline `EDITING` слово «редагування» означає аудит/аналіз, а не зміну target.

До `EDIT GATE` worker:
- не змінює target;
- не змінює README / INDEX / _COMMON / task-файли;
- пише тільки у REPORTS поточного run;
- не заявляє, що «внесе правки в арку».

01–34 повертають лише report/арбітраж. Зміна прози — окрема дозволена дія після gate.


Цей файл організує аналіз у кілька шарів. Основний принцип: **незалежні агенти не бачать звітів інших**, щоб не заражатися чужими висновками. Арбітри й оркестратор навпаки отримують звіти навмисно, але не голосують більшістю — вони перевіряють докази.

## Режими
- **ІНДИВІДУАЛЬНИЙ АГЕНТ — ТІЛЬКИ АКТУАЛЬНИЙ ТЕКСТ:** отримує лише файл, що аналізується. Не отримує старі аудити, рекапи, answer-key файли чи висновки інших агентів.
- **КОНТЕКСТНИЙ АГЕНТ — ТЕКСТ + ПЕРВИННІ ФАЙЛИ/GIT:** може читати репозиторій, сусідні арки, сирі логи й Git-історію. Похідні рекапи/валідації використовує лише як навігацію, не як істину.
- **АРБІТР — ТЕКСТ + ЗВІТИ:** отримує першоджерело і звіти агентів. Його задача — перевіряти їх, а не продовжувати їхні припущення.
- **ОРКЕСТРАТОР — ТЕКСТ + ВСІ ЗВІТИ + КОНТЕКСТ:** збирає доказову картину, аналізує також якість самих агентів і систематичні помилки пайплайна.

## Рекомендований порядок запуску
1. Паралельно й незалежно: №01–28.
2. Якщо оркестратор працюватиме в чистому чаті або без великої історії: №29 збирає нейтральний контекст-пак із первинних файлів і Git.
3. Після отримання індивідуальних звітів: №30-e (фаєрвол припущень), №31-e (anti-edit), №32-e (кластеризація), №33-e (контекстний фактчек).
4. №34-e-e проводить формальний мета-арбітраж цитат, чисел і конфліктів.
5. На основі №34-e-e + №30-e–33 автор/редактор визначає, які правки справді вносити.
6. Після правок: №35 запускається **свіжо й незалежно**, без звітів; потім №36 робить коректуру.
7. №37-e-e запускається останнім: отримує фінальний актуальний текст, усі звіти, арбітри, №35–36 і контекст; аналізує і текст, і якість самої системи агентів.

## Глобальне правило
Незалежність контекстів не означає незалежність модельних упереджень. Повтор однієї претензії багатьма саб-чатами — сигнал для перевірки, а не доказ. Авторські рішення з поточного чату, якщо вони доступні, мають бути передані оркестратору окремо; якщо їх немає, агент не має права їх вигадувати з тону комітів.

## Routing rule

Кожний файл задачі в цій папці містить власний routing front matter. Поля `required_reports`, `optional_reports` і `forbidden_reports` мають вищий операційний пріоритет для вибору вхідних REPORTS, але не змінюють зміст самого брифу.

Фізичний шлях до report-файла:
`AI_AGENT_PIPELINE/REPORTS/<target-key>/<run-folder>/EDITING/<task-id>__<YYYY-MM-DD_HH-mm-ss>_KYIV.md`.


`run-id` створюється для всієї редакторської кампанії і не змінюється після редагування цільового файла. Кожний звіт окремо фіксує blob SHA тієї версії тексту, яку реально аналізував.


## Report naming

Звіт зберігай як `<task-id>.md`. Час створення в report filename/metadata не фіксуй.

Повторний запуск: `<task-id>__retry-01.md`, `__retry-02.md` тощо.

Для required report за ID `04` використовуй `04.md`; якщо є COMPLETE retry — retry з найбільшим номером.

## Waiting protocol

Перед запуском будь-якого `DEPENDENT*` task перевір кожен `required_report`.

READY = файл існує, не порожній, має `Status: COMPLETE` і належить поточному run/target.

Якщо required input не READY:
- не починай аналіз;
- не симулюй відсутній звіт;
- не створюй COMPLETE report;
- поверни `WAITING_FOR_REPORTS` зі списком missing / claimed / incomplete IDs.

Для auto-dispatch допускається перейти до іншого runnable task цього pipeline. Якщо жодного runnable task немає — поверни `NO_RUNNABLE_TASKS`.

Звичайний GPT-чат не виконує фоновий polling сам по собі. Повторна перевірка відбувається при новому повідомленні/запуску або через окрему явно налаштовану automation.
