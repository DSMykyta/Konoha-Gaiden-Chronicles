# AI_AGENT_PIPELINE

Ця папка — єдина точка входу для ручного багаточатового пайплайна. Вона дозволяє запускати десятки незалежних ChatGPT-чатів короткою командою без копіювання великих промптів.

## Структура

```text
AI_AGENT_PIPELINE/
├── WRITING/
│   └── 30_plus_writing_pipeline_v1.md
├── EDITING/
│   └── 30_agents_v2.md
├── REPORTS/
│   └── README.md
└── README.md
```

- `WRITING/` — брифи для написання, розширення й побудови літературної прози.
- `EDITING/` — брифи для незалежного аналізу, чистки, редактури, арбітражу та фінальної оркестрації.
- `REPORTS/` — результати запусків. Сирі звіти не змішуються з файлами арок.

## Головне правило

Файл, який користувач назвав об'єктом роботи, є цільовим файлом. Агент не має права мовчки замінювати його старою версією, рекапом, summary, попереднім аудитом або іншим похідним файлом.

Сам бриф визначає, який контекст дозволено читати:
- якщо режим каже `ТІЛЬКИ АКТУАЛЬНИЙ ТЕКСТ` — не читай звіти інших агентів і не підтягуй Git/сусідні файли як джерело істини;
- якщо режим дозволяє `ПЕРВИННІ ФАЙЛИ/GIT` — можна читати дозволені первинні джерела;
- якщо це `АРБІТР` або `ОРКЕСТРАТОР` — читай лише ті звіти, які передбачені самим брифом.

Ніколи не порушуй незалежність агентів заради зручності.

## Короткий формат команди

Користувач може написати:

```text
Файл: <repo-relative-path>
Виконай EDITING/02.
```

або:

```text
Файл: <repo-relative-path>
Виконай WRITING/07.
```

Допустимі також спеціальні ID із master-файлів: `К0`, `Д1`, `Д2`, `Д3`, `А1`…`А5`, `W1`…`W7`, `O1`, а для EDITING — також `28`, `29`, `30`, `31`.

Цього достатньо. Не вимагай від користувача копіювати текст брифу в чат.

## Алгоритм worker-чату

1. Відкрий цільовий файл за repo-relative path і зафіксуй його Git blob SHA.
2. Відкрий відповідний master-файл:
   - `EDITING/<id>` → `AI_AGENT_PIPELINE/EDITING/30_agents_v2.md`;
   - `WRITING/<id>` → `AI_AGENT_PIPELINE/WRITING/30_plus_writing_pipeline_v1.md`.
3. Знайди точний бриф за ID і виконай його повністю, включно з режимом, методом, обмеженнями та форматом видачі.
4. Не читай звіти інших агентів, якщо твій бриф прямо цього не дозволяє.
5. Не редагуй цільовий літературний файл, якщо бриф прямо не вимагає створити/відредагувати прозу.
6. Збережи результат у `AI_AGENT_PIPELINE/REPORTS/` за правилами нижче.
7. У відповіді користувачу дай тільки короткий статус: який ID виконано і куди записано результат.

## Куди зберігати звіти

Для кожного стану цільового файла використовується окремий набір звітів, прив'язаний до blob SHA самого цільового файла, а не до HEAD репозиторію. Це важливо: коміти зі звітами змінюють HEAD, але не повинні розкидати один запуск по різних папках.

Формат:

```text
AI_AGENT_PIPELINE/REPORTS/
└── <target-key>/
    └── <source-blob-sha8>/
        ├── EDITING/
        │   ├── 01.md
        │   ├── 02.md
        │   ├── ...
        │   ├── A1.md
        │   └── O1.md
        └── WRITING/
            ├── K0.md
            ├── 01.md
            ├── ...
            ├── W3.md
            └── O1.md
```

`<target-key>` = ім'я цільового файла без розширення, нормалізоване для шляху. Якщо в репозиторії є кілька файлів з однаковим ім'ям, додай короткий стабільний префікс із батьківської папки.

`<source-blob-sha8>` = перші 8 символів Git blob SHA саме цільового файла.

Приклад:

```text
AI_AGENT_PIPELINE/REPORTS/
└── TEAM_9__arc_12_Довга_місія_База_2/
    └── a1b2c3d4/
        └── EDITING/
            ├── 01.md
            ├── 02.md
            └── A1.md
```

## Заголовок кожного звіту

Кожний звіт починай з:

```markdown
# <MODE>/<ID> — <назва брифу>

- Target: `<repo-relative-path>`
- Source blob SHA: `<full sha>`
- Prompt source: `AI_AGENT_PIPELINE/<MODE>/<master-file>`
- Task ID: `<ID>`
- Status: COMPLETE
```

Після цього — тільки результат, якого вимагає бриф.

## Якщо файл звіту вже існує

Не перезаписуй готовий звіт мовчки.

- Якщо той самий ID уже існує для того самого blob SHA — прочитай його статус.
- Якщо `Status: COMPLETE` — повідом користувачу, що задача вже виконана, і не запускай повторно без прямої команди `повтори` / `retry`.
- Для примусового повтору збережи `<ID>__retry-01.md`, потім `retry-02` тощо.

## Залежні задачі

Незалежні агенти виконуються окремо. Арбітри й оркестратори запускаються тільки після наявності потрібних їм звітів.

EDITING дотримується порядку, визначеного в `30_agents_v2.md`: незалежні №01–27 + Д1; за потреби К0; потім А1–А4; №28; після внесення правок незалежні №29 і №30; O1 останнім. №31 — окремий фінальний синтезатор, якщо він потрібен.

WRITING дотримується порядку, визначеного в `30_plus_writing_pipeline_v1.md`: К0; незалежні №01–24; за потреби Д1–Д3; потім А1–А5; W1; W2; W3; W4–W7; O1.

Якщо залежності відсутні, не вигадуй їхній зміст. Запиши статус `BLOCKED` і перелік відсутніх report-файлів.

## Команда для арбітра / оркестратора

Користувачу достатньо написати:

```text
Файл: <repo-relative-path>
Виконай EDITING/A1.
```

або:

```text
Файл: <repo-relative-path>
Виконай EDITING/O1.
```

Агент сам:
1. визначає blob SHA цільового файла;
2. знаходить відповідну папку `REPORTS/<target-key>/<sha8>/`;
3. читає тільки дозволені брифом звіти;
4. записує власний результат у ту саму папку.

## Важливо при правках самого тексту

Коли після арбітражу користувач окремо наказує внести правки в цільовий файл, blob SHA зміниться. Усі наступні аудити нового тексту автоматично повинні йти в нову папку з новим SHA. Старі звіти не видаляються: вони залишаються історією попереднього стану тексту.

Це запобігає змішуванню аналізів різних редакцій.

## Мінімальні команди для користувача

```text
Файл: KONOHA.../arc 12 [Довга місія — База 2].txt
Виконай EDITING/04.
```

```text
Файл: KONOHA.../arc 12 [Довга місія — База 2].txt
Виконай WRITING/12.
```

```text
Файл: KONOHA.../arc 12 [Довга місія — База 2].txt
Виконай EDITING/O1.
```

Жодного копіювання повного промпту в чат не потрібно.
