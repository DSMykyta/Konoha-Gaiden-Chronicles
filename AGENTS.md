# AGENTS.md — правила для AI-агентів Konoha Gaiden Chronicles

Цей файл застосовується до всього репозиторію. Призначення: мінімальні обґрунтовані зміни, збереження авторських рішень, перевірювана хронологія та стабільний SITE. Правила адаптовані з підходу до project-specific AI coding rules; це не автоматичний запуск тестів чи плагін.

## 0. Чотири обов'язкові правила для всіх агентів і чатів

1. **Не впевнений — запитай.** Якщо невизначеність впливає на результат, постав одне конкретне запитання до внесення змін. Якщо не блокує роботу — явно познач припущення, не видавай його за факт.
2. **50 рядків, а не 200.** Віддавай перевагу малим, завершеним патчам (орієнтир — до 50 змінених рядків за крок), а не масштабному переписуванню. Якщо завдання потребує більшого обсягу, коротко поясни чому; не обрізай необхідні тести, дані чи звіти.
3. **Чіпай лише потрібне.** Не змінюй сусідній код, історії, ID, форматування або структуру без прямого зв'язку із завданням. Не здійснюй попутні «покращення».
4. **Спочатку — як перевірити.** Ще до редагування визнач очікуваний результат і спосіб його перевірки: конкретний тест, валідатор або ручну звірку. Після змін повідом, що реально перевірено, а що ні.

## 1. Перед початком роботи

1. Прочитай запит користувача, `README.md` і документацію саме тієї підсистеми, яку змінюєш. Для сюжетних текстів у `AI_AGENT_PIPELINE/` його власні інструкції та EDIT GATE мають пріоритет у відповідному процесі.
2. Перевір поточні файли у **робочій гілці**, а `main` використовуй для окремого порівняння. Не покладайся на старі звіти, пам'ять, назви каталогів чи згенерований сайт. Розбіжності між кодом, документацією та даними спочатку зафіксуй.
3. Змінюй лише те, що необхідно для конкретного завдання. Не роби сторонніх рефакторингів, перейменувань ID, глобального переформатування YAML чи переписування вже прийнятого сюжету.
4. Перед кількома пов'язаними змінами сформулюй короткий план; після змін покажи точні файли, перевірки, невирішені питання й коміт. Не заявляй про успішний тест, якщо його не запускав.
5. Невідоме залишай невідомим. Не домислюй дату, місце, дію, мотив, джерело, згоду персонажа або фізичну присутність тільки для заповнення прогалини.

## 2. Де лежать авторитетні дані

- Поточний `SITE/scripts/build.mjs` читає YAML з `00_MAIN_WORK_FOLDER/CHRONOLOGY/data/` (відносно кореня репозиторію). Саме шлях у чинному скрипті збірки перевіряй перед роботою: деякі старі README й аудити посилаються на `KONOHA_GAIDEN_ARCS_ZIGRANE_POV_V3/CHRONOLOGY/data/`.
- `00_MAIN_WORK_FOLDER/CHRONOLOGY/data/README.md` описує схему, джерела, шари та редакторську відповідальність. Додаткові правила: `00_MAIN_WORK_FOLDER/CHRONOLOGY/Naruto_Timeline_Architecture_UA.md`, `EDITORIAL_DECISIONS_UA.md`, `SERIES_SOURCE_SYNC_PROGRESS_UA.md`.
- `SITE/` — read-only атлас; `SITE/public/data.json` і `SITE/public/version.json` генерує збірка. Не виправляй хронологію вручну в цих файлах.
- `AI_AGENT_PIPELINE/` — окремий багаточатовий процес написання/аудиту прози. Команда «Редагування» сама по собі НЕ дає права змінювати літературний target: дотримуйся `AI_AGENT_PIPELINE/README.md` і EDIT GATE.
- Дивись актуальні `time-anchors.yaml`, `timeline-periods.yaml`, `mission-windows.yaml` та інші реєстри; не фіксуй «назавжди» рік випуску або номер поточного року в коді чи правилах: робоча шкала може змінюватися.

## 3. Правила хронології Naruto

- Ієрархія: **момент → сцена → епізод → арка**. Вихідні посилання: `scene.episode_id` і `episode.arc_id`; похідні списки `scene_ids`, `episode_ids` та обчислені межі дат створює SITE. Кожна сцена має належати епізоду; не дублюй одну подію для різних ліній персонажів.
- Зберігай сталі ID, походження (`origin`, `evidence_ids`, `continuity_id`) та авторське рішення про шар (`canon`, `filler`, `sources`, `project`). `project` — авторські історії, навіть якщо вони використовують матеріали іншого формату. Не змішуй канон, аніме-доповнення, ігри, новели, OVA та власну історію непомітно.
- Розрізняй фізичну присутність (`physical` / `physical_hidden`), згадку, спостереження, повідомлення та віддалену участь. Згаданий персонаж не стає учасником місця події.
- **Паралельність дозволена**: події різних груп можуть відбуватися одночасно, навіть в один день. Конфлікт виникає лише за доведеної несумісності часових інтервалів, реальної фізичної присутності, переміщень або встановлених причинно-наслідкових обмежень.
- Для підозри на перетин перевір: дату й точність `placement` / `anchor_id`; учасників конкретних моментів; локацію й географічні переходи; час дороги/відновлення та `mission-windows.yaml`; відомі `before`-зв'язки; `review` і докази. Розділяй підтверджену суперечність, можливий конфлікт, брак даних і коректну паралельну подію.
- `display_rank` і `day_part` не доводять абсолютний час. Зв'язок `before` додавай лише за підтвердженим порядком, не з естетичних міркувань. Не змінюй `placement` або статус впевненості, щоб лише розрідити чи вирівняти шкалу.
- Ретроспективи розміщуй за **часом зображеної події**, не за датою виходу серії чи моментом переказу. Якщо точного року немає, залишай невизначеність та, якщо доведено, відносні зв'язки.
- Сцена/момент мають описувати подію в історії, не редакторські метадані. Не множ «моменти» за кожну репліку. Окремі адаптації не повинні дублювати ту саму реальну подію.
- Не змінюй встановлені якорі, біографії, вікові стани та канонічні рішення без конкретної підстави. У разі колізії джерел — запиши обидва свідчення та рівень впевненості, не видавай авторську реконструкцію за офіційний канон.

## 4. Код і поведінка SITE

- Працюй із наявним стеком **Node.js 22+, JavaScript (ES modules), YAML, linkedom, Playwright** згідно з `SITE/package.json`. Не додавай React, Next.js, інший фреймворк, БД чи залежності без окремої потреби.
- Зберігай семантичні масштаби: **рік — арки, місяць — епізоди, тиждень — сцени, день — моменти**; однакова ширина календарних днів незалежно від кількості сцен.
- Не ламай географічно обґрунтовані лінії персонажів, плавні криві, роздільні фізичні касти, зум/панорамування, sticky-день, фільтри чотирьох шарів, множинний вибір ліній та окремий фокус.
- Зберігай ієрархічні картки, поведінку hover/pin, навігацію з клавіатури/дотику й доступність. Не відновлюй відкладений повноекранний читач без окремого запиту.
- Для виправлень UI додавай або оновлюй відповідні регресійні тести: логіка/DOM, браузерна взаємодія, мобільні й десктопні розміри. У Playwright використовуй стабільні локатори й очікування станів замість довільних затримок, де можливо. Дотримуйся фактичного стилю поточних тестів.
- Перед додаванням бібліотечних API, які можуть змінюватися, звіряй їх із документацією (зокрема через Context7, якщо він доступний). Не вигадуй методи чи прапорці.

## 5. Перевірка та звітність

За зміни структурованої хронології (з кореня репозиторію):

```sh
python 00_MAIN_WORK_FOLDER/CHRONOLOGY/validate_timeline.py
python 00_MAIN_WORK_FOLDER/CHRONOLOGY/validate_shippuden.py
```

За зміни SITE (з кореня репозиторію, після `npm --prefix SITE ci` за потреби):

```sh
npm --prefix SITE run check
npm --prefix SITE test
npm --prefix SITE run test:browser
```

Остання браузерна команда вимагає доступного Chromium; окремі browser-тести є у `SITE/package.json`. Якщо середовище не дозволяє запуск — так і повідом, без вигадування результатів. Для суто документаційних змін достатньо перевірити зміст, шляхи та відповідність чинним скриптам; не запускай важку збірку без потреби.

- Для **змістовних змін хронології** підтримуй `00_MAIN_WORK_FOLDER/CHRONOLOGY/EDITORIAL_DECISIONS_UA.md`: об'єкт/ID, **було → стало**, причина, першоджерело, упевненість, ризик, коміт. Посерійні звірки також фіксуй у `SERIES_SOURCE_SYNC_PROGRESS_UA.md`; не підмінюй ними одна одну.
- За запиту на аудит створюй або оновлюй **саме погоджений файл звіту** й розділяй: перевірено / підтверджений конфлікт / підозра / невідомо / паралельність допустима / запропонована зміна / фактично внесена зміна.
- Не роби автоматичного деплою заради документації, аудиту чи звичайного коміту. У `SITE/vercel.json` Git-деплой вимкнений; ручний деплой тільки за окремим запитом. Коміт до `main` не означає, що опублікований сайт оновився.
- Перед завершенням повідом: змінені шляхи, виконані/невиконані перевірки, відомі обмеження та посилання на коміт. Не називай правила гарантією безпомилковості — вони задають процес, а автоматичні валідатори перевіряють лише закодовані інваріанти.
